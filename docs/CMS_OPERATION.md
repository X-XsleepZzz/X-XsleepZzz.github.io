# 記事を書く・公開する

CMS導入PRの確認・マージ前は、公開サイトの管理画面はまだ使えない。以下は導入後の手順。
従来のMarkdown＋Gitによる投稿方法も引き続き使える。

## 最初の設定

1. GitHubアカウントの2要素認証を有効にする。
2. GitHubの **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token** を開く。
3. Resource ownerは自分のアカウント、Repository accessは **Only select repositories** を選び、`X-XsleepZzz.github.io`だけを指定する。
4. 有効期限を設定する（例: 30日）。Repository permissionsは **Contents: Read and write** と **Pull requests: Read and write** を指定。Metadataの読み取りは自動で付く。それ以外の権限は不要。
5. 発行したトークンをコピーする。チャット、記事、config.yml、GitHub Secretsには貼らない。
6. [管理画面](https://x-xsleepzzz.github.io/admin/)を自分専用の端末で開き、「Sign In Using Access Token」（アクセストークンでログイン）を選んで入力する。専用OAuthサーバーの設定は不要。

画面の表示言語によってボタン名は変わる。CMSはトークンをブラウザのLocal Storageへ保存するため、共有端末でログインしない。ログアウトしてもトークンの失効とは別なので、紛失時はGitHub側でRevokeする。

導入時にリポジトリの **Settings → General → Pull Requests → Allow squash merging** が有効か確認する。保護ルールがある場合、所有者のトークンでもマージが止まることがある。ルールを無効化する前にPRのエラーを確認する。

## 保存場所と公開範囲

| 状態 | 保存先 | 誰が読めるか |
| --- | --- | --- |
| 編集中・自動バックアップ | 今使っているブラウザ | 通常はその端末の利用者。共有端末では秘密とはいえない |
| 「保存」後 | 公開GitHubの作業ブランチとDraft PR | **第三者がGitHubで読める**。サイトに出ないことと秘密であることは別 |
| 「公開」して配信完了後 | mainとGitHub Pages | 一般公開 |

**非公開にしたい原稿はCMSからGitHubに保存しない。** メモアプリなど別の保存先を使う。GitHubへ送った情報は、後でPRやファイルを削除してもGit履歴・キャッシュ・コピーから完全に回収できない。

CMSにはブラウザ内の自動バックアップがあるが、サイトデータの削除、プライベートウィンドウの終了、端末故障で失われる可能性がある。重要な原稿は自分で別にも保存する。ブラウザ内バックアップは端末間で同期されない。

## 新しい記事を作る

1. 「記事」コレクションを選び、新規作成する。
2. タイトルと本文を入力。概要とカテゴリは任意。カテゴリは`Learning`、`Essays`、`Notes`。言語は`ja`（日本語）か`en`（英語）。
3. Slug欄に、URLの末尾を入力する。例: `backend-learning` → `/writing/backend-learning/`。半角小文字・数字・ハイフンで書く。**最初の保存後は変更できない。** タイトルを変えてもURLは同じ。
4. 「サイトに表示しない」は通常OFFのまま。ONは従来の`draft: true`であり、公開操作をしても記事ページを作らない。これをOFFにしただけでは、Preview WorkflowのPRはマージされない。
5. プレビューで確認する。まだGitHubへ送ってよい内容か判断する。
6. 「保存」で作業ブランチとPRを作成する。保存はサイトへの公開ではない。

## Markdownの書き方とプレビュー

本文はMarkdownの直接編集に限定している。見出しは`## 見出し`から始める。タイトルと日付はサイトが表示するので、本文へ重ねて書かなくてよい。

`**太字**`、`*斜体*`、`- 箇条書き`、`> 引用`、`[表示名](URL)`、`![画像の説明](/images/example.webp)`、表を使える。コードは3つのバッククォートで囲み、`python`、`typescript`、`sql`、`bash`などの言語を続けて書く。

CMS内のプレビューは構造や画像を確認するためのもの。Astroとフォント・余白・コードの配色・日付表示が同じとは限らない。PRごとのAstroプレビュー環境は今回導入していない。「プレビューを開く」リンクが出なくても保存失敗とは限らない。

HTMLを本文に入れることもできるが、他人から受け取ったスクリプトや信頼しないHTMLは貼らない。CMSのプレビューはサニタイズされるが、公開サイトは従来どおり著者のHTMLを扱う。

## 画像を追加する

- PNG、JPEG、WebPを基本とする。1枚 **2 MiB（2,097,152 bytes）以下**にしてからアップロードする。
- 「Assets」（Asset Library）を開き、「Upload New Assets」→「Choose Files」で選び、「Upload」で保存する。保存後の画像の公開パスをコピーして、本文の`![説明](/images/ファイル名)`へ挿入する。本文を読む人に伝わる代替テキストを書く。
- ファイルは`public/images/`、本文の参照は`/images/`になる。標準の命名設定で元の名前にUUIDが付くので、同じ名前の画像を通常アップロードしても既存画像を置き換えない。
- **Asset Libraryでのアップロード・置換・削除は記事のPreview Workflowとは別で、直接mainへ保存される。** サイトのビルドが始まるので、公開してよい画像だけを扱う。この記事管理では本文をMarkdownの直接編集に限定している。公開前の記事で使う画像も、アップロードした段階でURLから閲覧できるものとして扱う。
- 画像に写った個人情報・著作権・撮影位置情報を確認する。**EXIFの自動削除はしていない。** 写真は公開前に位置情報などを除去して書き出す。
- 既存画像を「Replace」で置き換える操作や、手動のファイル名変更は意図的な上書きになる。通常の追加と区別する。
- 未使用画像の自動削除はしない。削除前にGitHub検索で`/images/ファイル名`を探し、他の記事で使っていないことを確認する。参照が残る画像を削除するとリンク切れになる。

## 公開する

1. 保存が成功したことと、本文・画像を確認する。
2. CMSの「Publish Entry」（公開）を選び、確認ダイアログで明示的に公開する。PRがmainへsquashマージされる。
3. [Actions](https://github.com/X-XsleepZzz/X-XsleepZzz.github.io/actions)で **Deploy Notes to GitHub Pages** のbuildとdeployが両方成功するまで待つ。
4. 記事URLを開き、本文・画像を確認する。古い表示なら再読み込みする。

**GitHubへの保存成功、PRのマージ成功、Pagesへの配信完了は別の段階。** CMSで公開操作が成功しても、Actionsが失敗・実行待ちならWebサイトの更新は完了していない。

公開日・更新日は従来どおりGitから自動計算する。PR内で最初に保存した日ではなく、mainへ初めて反映したコミットの日を日本時間で表示する。既存の`publishedAt`/`updatedAt`の手動指定値はCMS編集でも保持する。日付の例外的な入力は従来のMarkdown編集で行い、普段はCMSに日付を入れない。

## 公開済み記事を修正・削除する

「記事」から対象を開いて編集し、保存→プレビュー→公開→Actions確認の順に進める。編集途中は作業PRに保存され、既存の公開記事はそのまま残る。公開日は保持され、本文・タイトル・カテゴリなどの変更をmainへ反映した日が更新日になる。

削除は対象を選び、削除確認ダイアログをよく読む。公開済み記事の削除は直接mainに反映される場合がある。GitHubでファイルが消えたこととActionsを確認する。URLにアクセスしていた人は404になるので、必要な記事を誤って削除しない。

## 保存・公開に失敗したら

- **トークン期限切れ・401**: GitHubで新しいFine-grained tokenを発行し、再ログインする。古いトークンはRevokeする。
- **403 / Resource not accessible**: 対象リポジトリとContents・Pull requests両方のRead and writeを確認する。Contentsだけだとブランチ作成後にPR作成で失敗することがある。権限を直して再保存する。
- **通信切断・GitHub障害**: 原稿をローカルにもコピーし、再接続後にPR/コミットを確認してから再試行する。失敗ダイアログが出たのに保存済みと判断しない。
- **他端末からの同時編集**: 上書きする前にPRの差分と最新ファイルを比較する。自分の原稿を別にコピーし、再読み込みして変更を統合する。
- **マージできない**: PRの競合、保護ルール、トークン権限、squash mergeの許可を確認する。
- **Actionsのビルド失敗**: Actionsの失敗ステップを開く。日付・言語・カテゴリのFrontmatterなどを確認する。mainへの保存だけでは配信完了ではなく、通常は直前の成功版が表示される。修正後に再公開する。

誤って公開した場合、公開リポジトリ上で対象PRをRevertして新しいPRをマージするか、手動で直前の原稿へ戻してコミット・pushする。Actions成功後にURLを確認する。漏れたトークンは記事を消すだけでなく即座に失効させる。

## CMSが使えないとき・撤去するとき

従来どおり`templates/article.md`を`src/content/writing/<slug>.md`にコピーして執筆し、`draft: false`でコミットする。`npm run check`、`npm test`、`npm run build`を実行してからmainへpushする。詳しい手順はREADMEを参照。記事とGit履歴はCMS専用データではない。

CMSを撤去するには`public/admin/`を削除し、この導入PRをrevertする。CMSだけを取り除く場合はコピー元の日付を継承しない修正を残してよい。CMS用テスト・npmコマンド・ドキュメントも不要なら取り除く。既存記事・画像・テンプレート・日付計算・Pages設定は残す。未公開のCMS作業PRは内容を確認して個別に閉じ、不要なブランチを整理する。トークンを失効させ、ブラウザのCMSのサイトデータも削除する。

CMSのバージョンを更新するときは、`public/admin/index.html`のバージョンとSRIを一緒に更新し、`docs/CMS_VERIFICATION.md`の試験を再実施する。固定版は自動でセキュリティ修正を受け取らない。

## 本番導入前に残っている確認

ユーザー確認後にCMS導入PRをマージし、本人が上記の限定PATでログインする。安全なテスト用リポジトリで保存→Draft PR→公開→マージ→Actionsを先に確認することを推奨する。本番の既存記事・テスト記事を使った公開は確認後に行う。ローカルの仮想リポジトリ試験は、GitHubが実際に権限を許可した証拠にはならない。
